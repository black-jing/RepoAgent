# Repository Agent 面试问答

| 问题 | 简短回答 |
|---|---|
| 什么是 Agent？ | 模型围绕目标，依据观察逐步决定下一步动作并在适当时结束；外部工具由程序执行。 |
| 与普通 LLM 调用、固定 Workflow 有什么区别？ | 普通调用一次生成文本；固定 Workflow 的步骤预先写死；这里每轮都由模型从 5 个工具或 FINISH 中选择，路径可因问题与观察改变。 |
| Tool Calling 是什么？ | 把工具名称、说明和参数 schema 给模型，模型返回结构化工具请求。请求本身不执行，Java 验证后执行。 |
| Observation 是什么？ | 工具运行后的有限结果，例如读取的路径和代码片段；放回下一轮上下文供模型重新判断。 |
| 为什么要 State？ | 它记录问题、已调用动作、已读文件和有限证据；既防重复，也让模型知道已经查到了什么。 |
| 如何决定下一步和结束？ | LLM 根据 State 选单个 Tool Call 或普通答案；普通答案是主动 FINISH。Java 另外设置 maxSteps=10。 |
| 一直调用同一个 Tool？ | 相同 Tool+参数只执行一次，后续返回错误 Observation；连续 3 次工具错误退出。 |
| Tool 失败怎么办？ | 参数或文件错误写成 Observation，模型可改路径；GitHub 临时失败有限重试；LLM 失败退出并返回原因。 |
| 为什么限制 readFile 和上下文？ | 大文件会挤掉关键证据，增加成本。单次最多 6000 字符，State 只保留最近观察及短证据，早期原文不常驻。 |
| 为什么工具由 Java 执行？ | Java 能确定性地限制 URL、路径、输出、次数和时间；LLM 负责语义判断“接下来该查什么”。 |
| 为什么没有 RAG、Embedding、MCP、多 Agent？ | 目标是按需探索单个公开仓库；5 个只读 Tool 足以显示 Agent Loop。扩展机制会扩大范围和讲解成本。 |
| 为什么不允许 Shell？ | 只读 Github 文件就能回答目标问题，执行命令会引入无关权限和风险。 |
| 怎样证明是真 Agent？ | 看真实 LLM 的多问题 Trace：工具顺序、次数、读取文件、结束步数不同，而且 Observation 改变了后续选择。当前只有 Mock 决策的机制证明；真实 LLM 的这项验收还没完成。 |

## STAR 素材

- **S**：面对陌生 GitHub 仓库，要手动找 README、目录和调用链。
- **T**：做一个只读 Agent，根据问题逐轮选取需查看的文件。
- **A**：用 Java 21 + Spring AI 实现原生 Tool Call 的显式 Agent Loop，5 个 GitHub 工具、State/Observation、主动 FINISH、10 步上限、路径校验、部分搜索、短上下文与 Trace。
- **R（当前可核实）**：10 个确定性单元测试通过；4 个公开仓库的脚本化网络冒烟首次 4/4 读到预设路径，共 11 步、7 次 Tool Call。**这不等于真实 LLM 自主完成 4/4，也不是回答正确率。**真实模型结果、平均端到端耗时和成功率暂不填。
